# PPT 大纲：从聊天室到会调度、有记忆的 Super-agent

> 建议 12 页，讲述 8–10 分钟。每页给出「标题 / 要点 / 视觉 / 口播」。
> 图表文件都在 `docs/assets/`，可直接插入 PPT。

---

## 第 1 页 · 封面

**标题**：从一个聊天室，到一个会调度、有记忆的 Super-agent  
**副标题**：任务紧急度 · 个人记忆库 · 群聊关系图 · Harness 执行  
**视觉**：项目首页截图 + 右侧 Agent 面板截图  
**口播**：

> 我们做的不是一个更大的聊天框，而是把任务调度、个人记忆、协作关系和真实执行放进同一个 Agent 系统。

---

## 第 2 页 · 为什么现有 Agent 不够

**标题**：单 Session 的三道墙

**要点**：

- 任务无序：FIFO 队列，紧急任务靠人催；
- 记忆断裂：换个会话、换个信道，上下文就丢了；
- 协作盲区：Agent 不知道「这件事该找谁」。

**视觉**：三联问题卡片（调度 / 记忆 / 关系）  
**口播**：

> 单任务能力已经不是瓶颈，人的注意力和任务编排才是。我们要解决的是「多任务、多会话、多人协作」下的失控。

---

## 第 3 页 · 总体方案

**标题**：Router + Worker + Project + Memory

**要点**：

- Router：对话、分派、汇总；
- Worker：独立上下文执行，Harness 提供真实工具；
- Project：项目级上下文与工作区分区；
- Memory：个人记忆 + 群聊关系图。

**视觉**：架构图  
```text
用户 / GitHub / IM
        ↓
      Router
   ↓         ↓
Worker A   Worker B
   ↓
Harness / 项目 worktree
   ↓
个人记忆库 + 关系图
```
**口播**：

> 双层架构解决并发和上下文隔离，Project 解决项目分区，Memory 解决连续性和协作洞察。

---

## 第 4 页 · 亮点一：任务紧急度调度

**标题**：让紧急任务先跑，而不是让嗓门大的先跑

**要点**：

- 项目优先级 × 任务紧急度 × 资源权重；
- 等待时间老化，避免低优先级永久饥饿；
- 配额是软约束，高优先级仍可突破；
- 公式：
  ```text
  score = 项目优先级×100 + 紧急度×10 + 等待分钟×老化 + 权重加成
  ```

**视觉**：调度公式卡片 + 三个项目标签（核心平台 / 增长实验 / 技术债）  
**口播**：

> 我们把「紧急」变成可计算的分数，而不是靠人盯队列。核心项目 P5，技术债 P1，但技术债等久了会被老化抬上来，保证不会饿死。

---

## 第 5 页 · 实验一：调度效果

**标题**：紧急任务等待下降 70%，吞吐不变

**要点**：

- 150 任务 / 3 项目 / 4 Worker / 固定种子；
- 紧急任务平均等待：34.1s → 10.3s（-70%）；
- 紧急任务 P95：63.2s → 34.6s（-45%）；
- 核心项目平均等待：35.9s → 8.3s（-77%）；
- 吞吐：8.03 → 7.98 任务/分钟；
- 代价：低优先级最大等待约 6.5 分钟，由老化兜底。

**视觉**：
- `docs/assets/scheduling_metrics.png`
- `docs/assets/scheduling_wait_cdf.png`
- 可加 `docs/assets/scheduling_projects.png`

**口播**：

> 这里没有隐藏代价：低优先级确实等得更久，但我们把它限制在分钟级，不会无限饥饿。这是一个可解释的工程权衡。

---

## 第 6 页 · 亮点二：个人数据库

**标题**：每个用户一个独立的记忆空间

**要点**：

- SQLite 按 `user_id` 隔离，任何召回都必须带用户；
- 作用域：私聊 vs 项目；
- 类型：偏好 / 事实 / 决策 / 待办；
- 重要度 1–5，影响召回排序；
- 支持遗忘，用户可删除自己的记忆；
- 隐私：个人记忆默认只进私聊。

**视觉**：表结构简图 + 一条记忆示例  
```text
用户 A → 偏好「先结论后细节」→ 私聊注入
用户 B → 偏好「详细推导」→ 不会看到 A 的记忆
```

**口播**：

> 记忆不是把所有聊天记录塞进上下文，而是按人、按作用域、按重要度管理。A 的偏好不会泄漏给 B。

---

## 第 7 页 · 亮点三：群聊关系图

**标题**：从消息流里长出协作网络

**要点**：

- 同一 Thread 的相邻发言构建共现边；
- 节点大小 = 发言量；
- 边权 = 共现强度；
- 社区发现识别协作圈；
- 可识别核心连接者、信息孤岛、单点风险。

**视觉**：`docs/assets/relationship_graph.png`  
**口播**：

> 这张图不是装饰。它能让 Agent 判断「这件事该找谁」，也能帮团队发现过度依赖某一个人的风险。

---

## 第 8 页 · 实验二：关系图指标

**标题**：15 个成员、44 条边、4 个社区

**要点**：

- 节点 15，边 44，密度 0.419，平均度 5.87；
- 社区 4 个，对应不同的协作圈；
- Top 关系：测试–运维、算法–数据、后端–开源；
- 可用于任务路由、周报、组织健康度。

**视觉**：关系图局部放大 + 指标卡  
**口播**：

> 这些指标可以持续跑，形成「协作健康度」的时间序列，而不是一次性截图。

---

## 第 9 页 · 亮点四：Harness 真实执行

**标题**：Worker 不是模拟，是 DeepSeek Harness

**要点**：

- `dsh --profile headless --json` 执行真实编码任务；
- 真实工具、沙箱、Session 恢复；
- 任务独立 worktree，项目分区；
- Router 只分派，Worker 只执行，结果统一回传。

**视觉**：任务卡截图 + Harness 事件流片段  
**口播**：

> 我们的 Agent 能真的读文件、改代码、跑任务，而不是只生成一段文字。

---

## 第 10 页 · 连续性与项目分区路线

**标题**：下一步：一个 Agent，多个信道，多个项目

**要点**：

- Project / Thread / Subscription / Ticket 领域模型；
- Router 跨 Thread 记忆与 `attach_thread`；
- GitHub + IM 多信道；
- 项目级 worktree 与物理隔离；
- SQLite 持久化与重启恢复。

**视觉**：`docs/continuity-design.md` 的架构图 + 路线图时间轴  
**口播**：

> 官方原型的连续性是 Ticket/Thread 级的，我们借鉴它的模型，先做单项目连续，再扩到多项目和多信道。

---

## 第 11 页 · Demo 流程

**标题**：60 秒演示

**要点**：

1. 在房间 @Agent，派一个任务；
2. 右侧面板显示排队、优先级、执行轨迹；
3. 另一个用户发消息，关系图和在线成员更新；
4. 打开记忆面板，展示个人偏好；
5. 停止任务 / 查看 Harness 结果。

**视觉**：录屏或实时 Demo  
**口播**：

> 重点看三件事：任务有没有按优先级排队、Agent 有没有记住人、执行是不是真的发生了。

---

## 第 12 页 · 总结与优势

**标题**：我们交付的不是功能堆叠，是一套可调度的 Agent 基础设施

**要点**：

- 调度：从 FIFO 到项目优先级 + 紧急度 + 老化；
- 记忆：按用户隔离，可召回、可遗忘；
- 关系：群聊关系图与社区发现；
- 执行：Harness 真实 Worker + 项目分区；
- 论证：可复现实验、指标、图表。

**视觉**：四个关键词卡片：调度 / 记忆 / 关系 / 执行  
**口播**：

> 如果只记住一句话：我们把任务、记忆、关系和执行，放进了同一个可调度、可解释、可扩展的 Agent 系统。
