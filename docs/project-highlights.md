# 项目亮点与优势

> 一句话定位：把「一个聊天室」升级成「会调度、有记忆、能连续协作的 Super-agent 入口」。

---

## 亮点一：任务紧急度调度

### 解决什么问题

传统 FIFO 队列里，技术债、低优先级需求会和线上故障抢同一个 Worker 池。任务一多，真正紧急的工作被排在后面，人的注意力也被迫用于「盯队列」。

### 我们的做法

每个项目有优先级和资源权重，每个任务有紧急度：

```text
score = 项目优先级 × 100
      + 任务紧急度 × 10
      + 等待分钟 × 老化系数
      + 项目权重加成
      + 配额内加成（软约束）
```

调度器同时考虑：

- **项目优先级**：核心平台 > 增长实验 > 技术债；
- **任务紧急度**：low / normal / high / urgent；
- **资源权重**：按项目分配并发槽位；
- **老化**：等待越久分数越高，避免低优先级任务永久饥饿；
- **软配额**：配额内项目获得加成，但高优先级任务仍可突破配额。

实现位置：

- `backend/agent/task_scheduler.py`
- `backend/tests/test_scheduler_memory.py`
- 实验脚本：`experiments/generate_report.py`

### 实验设置

- 150 个任务，3 个项目，4 个并发 Worker；
- 15 分钟模拟窗口；
- 项目配置：核心平台（P5，权重 0.5）、增长实验（P3，权重 0.3）、技术债（P1，权重 0.2）；
- 对比 FIFO 与「优先级 + 配额 + 老化」；
- 固定随机种子，可复现。

### 实验结果

| 指标 | FIFO | 优先级调度 | 变化 |
|---|---:|---:|---:|
| 紧急任务平均等待 | 34.1 s | 10.3 s | **-70%** |
| 紧急任务 P95 等待 | 63.2 s | 34.6 s | **-45%** |
| 核心项目平均等待 | 35.9 s | 8.3 s | **-77%** |
| 整体吞吐 | 8.03 任务/分钟 | 7.98 任务/分钟 | 基本不变 |
| 低优先级最大等待 | 73 s | 389 s | 作为公平性代价上升 |

结论：

- 紧急任务和核心项目响应显著变快，吞吐几乎不受影响；
- 低优先级任务用等待换取高优先级产能，但被老化机制限制在约 6.5 分钟内，不会无限饥饿；
- 这是一个可解释、可配置的工程权衡，而不是简单的「谁嗓门大谁先跑」。

## 亮点二：个人数据库与群聊关系图

### 个人记忆库

`backend/agent/memory.py` 提供按用户隔离的 SQLite 记忆层：

| 能力 | 说明 |
|---|---|
| 按人隔离 | 所有 `recall` 必须带 `user_id`，不会把一个用户的记忆注入给另一个用户 |
| 作用域 | `private`（仅私聊）与 `project:<id>`（项目内共享） |
| 类型 | preference / fact / decision / todo |
| 重要度 | 1–5，影响召回排序 |
| 检索 | 关键词 + 标签 + 重要度 + 时间；首版不引入向量库 |
| 遗忘 | `forget(user_id, memory_id)`，用户可删除自己的记忆 |
| 关系图 | 从群聊消息构建成员共现网络 |

隐私原则：

- 个人记忆默认只进私聊，不自动出现在公共房间；
- 项目记忆只在该项目的 Thread 内可见；
- 跨渠道身份只做展示别名，不作为授权依据。

### 群聊关系图

从同一 Thread 的相邻发言构建共现边：

- 节点：成员；
- 边：共同参与同一话题的强度；
- 节点大小：发言数量；
- 颜色：社区发现结果。

示例数据：

- 15 个成员、44 条边、4 个社区、平均度 5.87；
- 可以识别跨群连接者、沉默成员、核心协作圈。

图表：`docs/assets/relationship_graph.png`  
指标：`docs/assets/relationship_metrics.json`

用途：

- 帮 Agent 判断「这件事该找谁」；
- 识别信息孤岛和高风险单点；
- 为个人助手提供「我最近在和谁协作」的上下文；
- 未来可接入组织架构、任务归属和项目角色。

## 亮点三：可复现的实验数据

不是只讲概念，所有图表都能重新生成：

```powershell
python experiments/generate_report.py
```

脚本会：

- 生成 150 个任务、3 个项目的调度负载；
- 对比 FIFO 与优先级调度；
- 输出 JSON 指标；
- 生成 4 张 PNG：等待 CDF、关键指标、按项目等待、群聊关系图。

所有随机过程固定 seed，答辩时可以现场复跑。

## 亮点四：其他优势

### 1. 真正的 Harness Worker

Worker 不是模拟的：通过 `dsh --profile headless --json` 调用 DeepSeek Harness，具备真实编码工具、沙箱和 Session 恢复能力。

已验证：读取 README、执行真实模型调用、返回任务结果。

### 2. Router + Worker 双层架构

- Router 负责对话、分派、汇总；
- Worker 负责执行，上下文隔离；
- 同一 Thread 的后续消息直通 Worker；
- 支持停止任务、流式进度和工具轨迹。

### 3. 项目分区设计

- 每个项目一个工作区；
- 每个任务一个 worktree；
- 不同项目上下文不串；
- 后续可升级为「一个项目一个实例」的物理隔离。

### 4. 连续性与持久化路线

已经产出 `docs/continuity-design.md`：

- Project / Thread / Correlation / Subscription / Ticket 领域模型；
- Router 跨 Thread 记忆与 `attach_thread`；
- SQLite 持久化与重启恢复；
- GitHub / IM 多信道适配路线。

### 5. 安全与可解释性

- 个人记忆按用户隔离；
- 项目路径守卫；
- 任务优先级、等待时间、配额全部可解释；
- 实验指标可复现，不依赖「感觉更快」。

---

## 优势总结

| 维度 | 普通聊天室 | 我们的方案 |
|---|---|---|
| 任务调度 | FIFO，紧急任务靠人催 | 项目优先级 + 紧急度 + 权重 + 老化 |
| 记忆 | 无，刷新即丢 | 按用户隔离的 SQLite 记忆库 |
| 协作洞察 | 无 | 群聊关系图与社区发现 |
| 执行 | 只会聊天 | Harness 真实编码 Worker |
| 扩展 | 单会话 | Router/Worker + 项目分区 + 多信道路线 |
| 论证 | 主观描述 | 可复现实验 + 指标 + 图表 |

一句话：**我们不是再做一个聊天框，而是把「任务、记忆、关系、执行」放进同一个可调度的 Agent 系统里。**
